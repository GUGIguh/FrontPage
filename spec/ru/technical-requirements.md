# Технические требования

Задание поддерживает два пути: **full-stack** (рекомендуется) и **[только фронтенд](#альтернатива-только-фронтенд)**. Разделы ниже описывают full-stack-подход. Если ты предпочитаешь обойтись без аутентификации и базы данных, переходи к разделу «Альтернатива: только фронтенд» в конце — там объясняется, что меняется, а что остаётся прежним.

## База данных

Используй настоящий сервис баз данных — не localStorage и не хранение в памяти.

**Рекомендуемые варианты:** Supabase, Firebase, Neon, PlanetScale, Turso или аналог.

**Обязательно хранить:**

- Аккаунты пользователей и данные аутентификации
- Подписки на фиды (URL, название, категория, статус здоровья, время последней загрузки)
- Записи фидов (заголовок, описание, контент, автор, дата публикации, фид-источник, URL)
- Состояние прочитано/не прочитано для каждой пары «пользователь — запись»
- Закладки каждого пользователя
- Настройки пользователя (раскладка, интервал обновления, категории, порядок)

**О чём стоит подумать:**

- Как эффективно выбирать записи по фиду, И по категории, И по диапазону дат? Какие индексы нужны для таких запросов?
- Что происходит при удалении фида — какие связанные данные нужно подчистить (записи, состояние прочитанного, закладки)?
- Как ты справишься с пользователем, у которого 50 фидов в среднем по 20 записей = 1000+ записей? А если фидов 100?
- Когда загружать записи фидов (по запросу или в фоне) и как избежать дубликатов при повторной загрузке?
- Как хранить состояние прочитано/не прочитано для каждой пары «пользователь — запись» так, чтобы таблица не росла бесконечно?
- Какова стратегия дедупликации, когда при повторной загрузке та же запись приходит с немного изменённым содержимым?

## Аутентификация

Реализуй настоящую аутентификацию пользователей — не имитацию и не заглушку.

**Обязательные сценарии:**

- Регистрация (минимум email + пароль)
- Вход
- Выход
- Сброс пароля
- Сохранение сессии при обновлении страницы

**Рекомендуется:** использовать встроенную аутентификацию провайдера базы данных (Supabase Auth, Firebase Auth) или отдельный сервис аутентификации (Clerk, Auth0, NextAuth).

**Гостевой режим:** должен работать без аутентификации. Данные гостя живут в пределах сессии и не сохраняются.

## Загрузка фидов на стороне сервера

RSS-фиды нельзя загружать напрямую из браузера из-за ограничений CORS. Нужен серверный компонент.

**Варианты:**

- API-маршруты (Next.js, Nuxt, SvelteKit, Remix и т. д.)
- Edge-функции (Supabase Edge Functions, Vercel Edge Functions, Cloudflare Workers)
- Отдельный бэкенд (Express, Hono, Fastify и т. д.)
- Функции BaaS (Firebase Functions)

**Требования:**

- Загружать фиды на сервере и возвращать клиенту разобранный результат
- Корректно обрабатывать таймауты (таймаут 10 секунд на фид)
- Реализовать базовое ограничение частоты запросов, чтобы не перегружать источники фидов
- Кэшировать ответы, где возможно (учитывать заголовки Cache-Control, ETag, Last-Modified)
- Обрабатывать редиректы (301, 302) — следовать им и при постоянном редиректе обновлять сохранённый URL фида

## Деплой

Разверни приложение по живому, публично доступному URL.

**Рекомендуемые платформы:** Vercel, Netlify, Render, Fly.io или аналог.

**Требования:**

- Доступность по HTTPS
- Никаких зависимостей, существующих только локально (всё работает у любого посетителя)
- Переменные окружения настроены правильно (секреты не раскрыты)
- Приемлемое время холодного старта, если используется serverless

## Целевые показатели производительности

| Метрика | Цель |
|--------|--------|
| Время до интерактивности на лендинге | < 2 секунд |
| Первичная загрузка ленты (после входа) | < 3 секунд |
| Результаты поиска | < 500 мс |
| Прокрутка 100+ записей | Плавная (60 fps, без рывков) |
| Обновление отдельного фида | < 5 секунд |
| Сдвиг раскладки при загрузке | Минимальный (скелетоны/плейсхолдеры) |

## Выбор технологий

Задание **не привязано к фреймворку**. Используй то, с чем ты наиболее продуктивен.

**Распространённые варианты:**

- Next.js, Nuxt, SvelteKit, Remix, Astro (full-stack-фреймворки)
- React, Vue, Svelte, Solid (с отдельным бэкендом)
- Любой другой подход, удовлетворяющий требованиям

В стартовых файлах есть CSS-переменные и конфиг Tailwind v4, но ни CSS, ни Tailwind не обязательны. Используй любой подход к стилям, который тебе нравится.

## Альтернатива: только фронтенд

Разделы выше описывают рекомендованный full-stack-подход. Если ты сосредоточен на фронтенд-разработке и не готов реализовывать аутентификацию и базу данных, можно сделать версию только на фронтенде. Ниже объясняется, что меняется, а что остаётся прежним.

**Что заменяет базу данных:**

Используй localStorage (или IndexedDB для больших объёмов), чтобы хранить все данные пользователя: подписки на фиды, кэшированные записи, состояние прочитанного, закладки и настройки. Учитывай, что у localStorage лимит около 5 МБ на origin и что все данные живут в одном браузере — синхронизации между устройствами нет.

**Что меняется в продукте:**

- Нет аутентификации — приложение однопользовательское, без регистрации, входа и сброса пароля
- Нет понятия «гостевой режим» — есть просто приложение, и любой, кто его открыл, является пользователем
- На лендинге один призыв к действию («Начать» или «Открыть панель») вместо двух кнопок — регистрации и гостевого входа
- Нет синхронизации между устройствами — смена браузера или очистка хранилища означает начать заново
- Предзагруженные примеры фидов становятся стартовым состоянием по умолчанию, а не особенностью гостевого режима

**Что остаётся прежним:**

- Загрузка фидов на стороне сервера — по-прежнему обязательна из-за ограничений CORS
- Все функции управления фидами, чтения, поиска и раскладок
- Деплой по живому, публично доступному URL
- Целевые показатели производительности, перечисленные выше

**Компромисс, который стоит обдумать:**

Оба пути дают сильную работу для портфолио. Full-stack-версия демонстрирует дополнительные навыки (сценарии аутентификации, проектирование базы данных, защищённые маршруты, моделирование данных), а версия только на фронтенде позволяет сосредоточиться на мастерстве UI/UX, системах раскладки, парсинге RSS, управлении состоянием и фронтенд-инженерии. Выбирай путь, который соответствует твоему текущему уровню и целям обучения.
